# 共用核心架构（1.7.0）

## 可执行代码与边界

`prototype/shared/core` 是手机与网页场中主流程的唯一核心来源。手机通过 Metro 打包直接执行，网页通过统一事件接口调用后台常驻 Node 运行器，执行同一份 TypeScript；Python `shared_core.py` 只做调用转换，没有第二份规则算法或静默回退。

| 模块 | 职责 |
| --- | --- |
| roundEngine.ts | 规则校验、逐杆、事故与救济、成绩、切洞、撤销、旗位和球杆资料 |
| geometry.ts | WGS84距离、多边形与内环、表面分类、障碍穿越、落区宽度 |
| bag.ts | 已报告Carry、挖起杆范围/用途、7号铁暂估表、保底杆 |
| strategy.ts | 开球、直接攻果岭、滚入、过渡、五杆洞两上筛选和风险排序 |
| dialogue.ts | 有限的中文指令与结果表达；未知语句不写成击球事实 |
| protocol.ts | 核心版本、测试数据代次 |

后台保留账号、事件事务、单设备记录权、同步复核、历史存档与联网对话。地图整理和历史摘要准备留在后台。普通本机策略不请求网络，不每次加载完整历史。

**接入边界：网页场中事件已切换到`core_event`，规则、状态和策略由共用核心处理，不再回退旧Python场中算法。首次问答、身份、赛后分析与教练对话属于应用服务，继续复用后台。旧`action:event`及`/round-state`已退役并返回410，旧场中分支与兼容测试已删除。旧版无共用模型的测试局明确拒绝接管，不猜测迁移。**

`webJourney.ts`只把网页消息、地图和声音事件转换为共用指令，并管理提示、待补成绩与静默状态；实际击球、罚杆、成绩均经`roundEngine.ts`校验。地图选点仅移动；点击模拟击球明确记录；声音已登记的击球再提交落点只补位置。网页目前仍依赖服务连接，不是浏览器离线包。

后续扩展应优先增加共用核心指令，不另写手机/后台两份规则。现有核心仍不自动认证救济几何，也不猜测E-5、不可打球或尚未支持的规则例外。

## 手机执行路径

1. 首次账号认证和下载球场需要联网；已有本机身份后首次了解、Carry、选Tee和起始洞在本机完成。
2. 球场资料可提前下载；本机问答、Tee与起始洞选择及新建球局不依赖网络。开始时固定资料快照，联网后注册并同步独立球局。已有网页球局交接才使用两阶段记录权协议。
3. 击球、旗位、球杆Carry和球位更新先在本机校验、提交检查点后返回保存结果。
4. “这杆怎么打”“保守方案”“其他路线”等在手机直接计算。旗位、球位和触球条件不足时提出具体补问，不补猜坐标。
5. 联网同步原事件，后台同核心复核后写入正常成绩/逐杆来源；未验证回执不会删本机队列。

位置输入暂可使用明确的“球位 纬度,经度”，或标注为模拟的发球台参考点。真实GPS与麦克风资源仍需原生设备接线/验收，不能把数学模块迁移等同于已完成实机产品。

## 策略约束

- 默认单一开球建议，普通长草不等同罚杆区；不凭杆名认为球道木更安全。
- 保守/替代请求比较实际落区暴露、宽度、推进和保底杆；保底杆未知Carry先问，不猜其能力。
- 飞行瞄准线经过障碍不是直接淘汰条件；核对Carry落点与障碍远沿余量。地图提示OB/下水只询问现场确认，不自动加罚。
- 3号木等允许最多约10码条件性滚入；必须核对地图上的地面通道，不能把滚动当作保证。
- 五杆洞以公布洞长筛选两上，已知最长组合不足洞长减10码时不计算第二杆攻果岭几何。缺长杆资料先补问。估计落点后重算下一杆，不把开球台到果岭直线当洞长。
- 过渡不为固定“留90码”而截短；优先中铁/非木杆推进。只有足够宽、无已标障碍暴露的落区才考虑球道木过渡。
- 同球场、Tee和地图签名的最近五场只作为内部参考；单次失误不加重复风险权重，不播报历史参考，不用含滚动距离校准Carry。
- 旗位是本洞上下文，不是击球；确认球杆也不等于已经击球。球位变化保留球杆、清除过时目标，避免把旧瞄准点用于后续散布统计。

## 版本与缓存

`/journey` 声明 `offline_protocol:3` 与 `shared_core_version:1.7.0`。本机准备和固定包带核心版本。新球局用当前版本；既有1.4/1.5球局由版本运行器继续执行，包和模型版本混用或未知版本会拒绝。详见[升级续局](versioned-round-resume.md)。

手机仅缓存当前实例的一份策略；键含包摘要、球局ID、状态revision和意图。球位、旗位、球杆/Carry或球洞变化都会使其失效。地图几何缓存使用不可变地图对象的WeakMap，并分别隔离模拟与非模拟模式。

后台策略包缓存键含认证账号、聚合、租约与包摘要，每个Node工作进程最多8份/32MiB；后台现使用有界进程池。地图只在首次注册或缓存失效时传给常驻运行器；模型和意图每次来自当前认证球局。运行器重启后重注册；不自动重放写命令，不回退Python规则。`core_plan` 是只读接口，不接受客户端地图或状态作为事实来源。

## 运行与验证

后台需要 Node >=22.13，无法从PATH找到时设置 `CADDIE_NODE_BINARY`。开发缓存环境也会检测 Python 同级的 Node 运行时。服务在启动时预热核心，避免每次请求启动子进程。手机 Metro 已将 shared 目录纳入打包观察。

```sh
CADDIE_TEST_PYTHON=/path/to/python node --experimental-transform-types --test prototype/tests/*.test.mjs
PYTHONPATH=prototype python -m unittest discover -s prototype/tests -p 'test_*.py'
python -m unittest discover -s skills/golf-caddie/tests -p 'test_*.py'
node --experimental-transform-types prototype/scripts/benchmark_local_strategy.mjs
python -B prototype/scripts/run_local_tests.py --suite benchmark
```

宿主机 darwin arm64 / Python3.12 / Node24.22.3：同一凤凰山四、五杆洞发球场景，各5轮、60样本。旧Python策略函数p50/p95约2.641/37.114ms；共用后台策略约0.834/2.967ms。Node冷启动56.908ms，在服务启动时完成；首次地图注册计划25.360ms。算法与策略选择有所调整，此为同场景计算链路对比，不是相同输出算法的微基准。

手机核心在宿主机直接执行：含地图JSON解码与模型创建的冷输入p50/p95约3.279/5.180ms；热几何约0.889/1.947ms；100次未变计划缓存查询约0.003/0.006ms。测量不含原生文件读取、设备GPS、ASR、TTS、网络或语音端到端反馈，不能承诺手机同样的绝对时间。

## 网页接入与性能验证

网页主流程现发送`action:core_event`。开局固化一次地图、档案和最近五场参考；完整资料用不可变组件引用保存，普通消息不重复序列化地图。通用地图边界环、落区数据也改为按需读取。白桩演示线由地图适配层转换为有明确内侧参照的有限线段，核心不把普通球洞轮廓当作OB，也不无限延长白桩线。

双重去重覆盖相同operation_id重试，以及新operation_id重复提交相同event_id；改变原内容会拒绝。导航不新增击球、不补成绩，上一洞报分保持洞号作用域，且不会清除当前洞已选球杆。手机仍持有离线记录权时网页拒绝抢写；手机同步并释放后，网页可绑定同一固定包、继续原共用模型，未重建或猜补逐杆。

回放记录包含首个固定包和后续原始网页事件；后台通过同一核心重放，客户端不能提供自己的seed或状态。未知场中事件拒绝，不回退旧规则。赛后分析可读取投影结果，但包含改分/罚杆的混合语句不能借赛后服务绕过核心。

`benchmark_web_core.py`在darwin arm64、Python3.12/Node24、临时SQLite和本地HTTP上，凤凰山第1洞各30次询问、紧凑返回视图：旧入口p50/p95为10.104/11.518ms，共用入口为4.013/5.672ms。第一次询问约9.066ms。开局由81.703ms增至214.705ms，增加部分是一次性固化和注册地图资料，不隐藏此成本。测试不含浏览器渲染、ASR/TTS或真实网络，不能当作端到端语音指标；测试脚本不包含球洞专用优化逻辑。

网页部署后需刷新页面。当前匹配核心版本为1.7.0，原生构建必须使用匹配的核心；真机GPS/语音与原生完整构建仍未完成验收。


### 网页救济定位补充

暂定球转为使用中球后，先更新位置，再确认“已到暂定球位置”，保留原发球起点并补齐实际落点，不再新增击球。水障碍救济可逐项确认最后越界点、合法抛球、球停在救济区内，然后更新位置并说“确认在当前位置”。这些状态和确认条件均在同一规则核心中；坐标未知仍可明确选择未知，不编造距离。
