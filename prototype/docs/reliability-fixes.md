# 临时错误重试、健康探测与本地初始化修复

2026-11-23，后台基础设施补丁0.2.1；共用核心1.4.0、数据库schema与缓存版本不变，不清除任何球局。

## 临时错误的请求身份

手机JourneyClient、多语言客户端、中文网页及多语言网页对408/425/429和5xx保留原请求。重试仍使用原operation_id、event_id、内容与expected_version，不自动改为新请求，不自动循环发网络请求。明确拒绝的4xx（如409版本冲突）继续释放旧请求，让用户核对后重新决定。中文网页保留输入、显示重试按钮；语言测试页补齐原请求重试入口。

手机JourneyClient的待处理请求已持久化；临时错误后重启仍能恢复同一请求。多语言测试客户端和网页的重试仍仅在当前会话内保存，本轮未声称增加浏览器持久化。

故障回归覆盖限流、服务错误、手机重启与原请求身份一致。另实测服务端提交成功、渲染回执时故意产生500，原请求重试后事件与版本仍仅增加一次，避免把“错误响应”当作“肯定未执行”。

## 存活与就绪分开

`GET /health`只报告进程存活，位于应用并发门、业务限流、数据库、规则RPC与Redis调用之前。即使依赖不可用或业务并发已满，也不因此返回不存活。

`GET /ready`仍检查数据库、规则核心与Redis，任何依赖失败返回503；不消费业务限额，但仍受应用并发门保护。反向代理示例对/health单独路由，不套业务限流；/ready仅允许本机来源，实际监控网段需按部署环境明确配置。生产探测不应再把依赖故障转成全实例重启。

## PostgreSQL本机生命周期

开始、初始化和停止共享同一OS进程锁，等待上限30秒。配置使用权限0600的临时文件，fsync后原子替换，并同步父目录；配置损坏会明确报错，不覆盖数据库或猜造新密码。进程退出时OS自动释放文件锁，不把锁文件存在误当作永久占用。

真实双进程测试在独立临时集群中运行：两次启动都成功、initdb与pg_ctl start均仅执行一次，两次连接身份一致。另验证初始化中另一个启动者不会读取未完成配置、锁等待超时、持锁进程终止后可恢复、写配置失败保留原完整内容。此项针对POSIX开发启动器；不宣称通过硬件断电或Windows验收。

## 验证与性能

业务142项、客户端109项及PostgreSQL/API故障回归均通过。本轮累计350项通过，1项真实Redis共享限流检查因未配置本机Redis而未执行。核心类型、App/语音语法及Python语法检查通过。依赖不可用的健康检查使用故障注入验证，不冒充真实Redis故障切换。

同一macOS arm64/Python3.12/Node24环境、独立PostgreSQL、凤凰山第1洞30次紧凑HTTP询问：前一轮p50/p95=4.323/7.951ms，修复后4.553/7.789ms；首查询11.061→12.610ms，开局276.275→269.368ms。小样本对照未见明显热查询退化，不能将差值视为稳定提速；测试不含手机、ASR、TTS或真实网络。客户端只增加常数级错误分类，不增加后台请求或策略重算。
