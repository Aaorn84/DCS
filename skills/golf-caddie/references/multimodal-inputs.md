# 语音、GPS与球场数据联合维护球局

## 正式产品定义

用户可以只用语音完成交流与记录，不必逐杆点击；后台联合语音、GPS和球场数据维护结构化球局。语音是交互入口与行为证据，不能代替位置和地图。GPS和球场数据是商业产品的事实底座。

| 输入 | 回答什么 | 不能单独证明什么 |
| --- | --- | --- |
| 球场数据 | 这里有什么：洞布局、par、果岭、障碍、OB与罚杆区边界、推荐落点 | 当前旗位、边界现状、球手所在处或实际击球；推荐落点不是针对本人的决定 |
| GPS | 球员现在在哪里：定位、候选球洞、到目标/障碍的几何距离、候选起落点与换洞 | 手机必在球旁、已挥杆、已完成本洞、准确杆序、carry |
| 语音 | 本人说用了什么杆、想做什么、实际决定、感受、描述结果、成绩与纠正 | 未观测的精确落点、真实飞行距离或缺失杆序 |

地图原始几何、GPS原始观测、宿主计算的距离分别标来源、时间、单位、精度及版本。地图推荐落点属于场地参考，不自动转为当前选杆/瞄准策略。球场高差与果岭坡度目前不可用，保持null；不得当0。

## 三路证据的状态流程

1. 保存有版本的球场快照与GPS观测；地图/GPS对象匹配由宿主可信地理组件执行。
2. 语音结合待答问题、已知球洞/击球、定位时间和地图上下文生成候选解释；GPS不覆盖用户明确的过去洞号指代。
3. 保留多个合理解释；比较差异会不会改变当前问距、策略、罚杆或记录归属。
4. 无冲突且符合确认规则才提交；关键冲突问一个问题，静默或准备击球时暂缓；未知不填0。
5. 地图、位置或语音被修订时，相关派生距离、策略和待播内容按依赖失效；独立事实保留。

GPS判断手机在二号洞而用户补报一号洞成绩，两者可以同时成立，并不必然是冲突。定位匹配到相邻球洞、地图障碍与现场描述不符，则保留候选与原始证据，不用“GPS优先”或“语音优先”覆盖另一来源。

## 用户例子的准确落地

“我还是用了7铁，有点短，右边”：

- 原话与转写版本作为证据保留；实际7铁及短/右是本杆自报候选，待明确归因。
- 有已绑定击球或可靠上下文才确定归属；杆序不明则保持未知，不能根据当前位置自动断定“第二杆”。
- 起落点可从GPS与地图形成候选；确认是球位及同一杆后，才形成水平总距；不能冒充carry。
- 原建议必须查真实策略记录，不能由“还是”补造球童先前说过什么。
- “短”“右”均是本次观察；没有可比样本，不改变长期7铁carry或偏差画像。

本版保守中文适配器尚不直接解析这整句，须由宿主语义适配器产生候选；不能把设计示例当已识别能力。已实现证据入口与依赖门控可承接这些候选。

## v0.1.5交付接口

状态组件v0.2.0沿用evidence命令，source支持user/gps/course/sensor。course最小载荷：

```json
{
  "id": "course-c1-current-map",
  "revision": 1,
  "phase": "final",
  "source": "course",
  "observed_at": "2026-11-06T08:00:00+08:00",
  "data": {"course_id": "c1", "map_version": "map-20261106", "crs": "WGS84"}
}
```

同一球场快照更新使用同一id、更高revision，同时更新map_version。data可携带宿主验证后的洞布局与对象；本引擎只校验上述最小元数据，不进行完整GeoJSON、多边形拓扑、授权来源或对象语义校验。完整地图校验和距离/对象匹配仍由地理组件负责，不能把记录入口当测绘算法。

事实/派生依赖以外，新增`evidence:证据ID`引用，例如`evidence:course-c1-current-map:1`，版本为该证据revision+1。只有active final能作依赖；新final修订会失效旧证据关联的派生结果及语音任务。只依赖地图/GPS原始观测不能登记为已确认个人能力统计。

宿主应在计算时将实际使用的地图、GPS、语音与事实版本完整列入deps；漏列依赖，本引擎无法凭空知道计算用了哪份地图。三路输入汇合可以形成只读策略情境，但不会自行生成击球、杆序或成绩。

## 技术材料的分层

维护核心处理链：多轮事件归因、歧义对策略和状态的影响评估、证据不完整时的暂存、带版本的提交及回滚。

位置与地理增强层：GPS定位和换洞候选、起落点候选、球场对象匹配、跨来源冲突确认。三路证据是运行输入，核心处理链是系统处理机制；描述技术方案时同时写清二者，不写成仅语音输入或普通GPS距离播报。
