# GPS APP接入与逐场学习

本文件定义技能需要的数据与行为，不代表APP接口、长期记忆、GPS或后台语音已经接通。目前用户明确：GPS数据不含球道海拔与果岭坡度，后续计划增加。其他地图字段须由APP实际声明，不能把GPS定位等同于完整球场地图。

## 当前能力按字段开放

| 可用证据 | 可以做 | 不能据此做 |
|---|---|---|
| 带时间与精度的GPS坐标 | 定位候选、计算到已知目标的水平距离，位置可靠时减少重复问距离 | 自动确定挥杆、球位类型、球所在洞、处罚状态或落地距离 |
| 已核验的洞号、发球台、球洞地图与目标几何 | 在实际覆盖范围内解释落区、球洞走向、前中后与障碍距离 | 在只有洞中心点时生成边界、绕障路径或安全落区 |
| 果岭轮廓与当前旗位坐标 | 距离与平面目标讨论；区分旗位与果岭中心 | 没有旗位时用中心替代旗位而不说明；没有坡面时精确读线 |
| 经确认的击球起点、球杆、下一球静止终点 | 估计这次击球的水平起终点距离，建立按条件分组的结果样本 | 分离空中落地与滚动、把行走轨迹当球轨迹、忽略救济与漏杆 |
| 用户描述球位、坡向与现场风 | 作为带来源的现场信息参与交流 | 宣称是传感器测量、外推整洞地形或自动量化修正 |

当前海拔与坡度字段必须是null/ unavailable，不能用0表示平坦。距离标明“水平距离，未作高差补偿”，无需每次整段复述，但在高差会改变方案或用户问实际打多远时明确提醒。没有坡度时可交流用户的读线、速度感与推杆意图，不给精确转折、杯数或补偿距离；未知坡度也不阻断陪伴、记分和平面策略讨论。

## 推荐APP上下文契约

这是待开发的逻辑契约，不假定已有端点或工具名。每次建议只传必要信息，读写严格限定当前用户与球局；未经接口核验，不声称已经读取APP。

- 身份与会话：player_id、round_id、hole_id、shot_id（未确认可空）、request_id、上下文版本、时区与单位、赛制/规则状态、记忆授权范围。
- 能力声明：每个字段/工具是否可用、采集来源、观测时间；水平地图、高差、果岭坡面、旗位、天气、击球检测、存储读写各自声明，不能单个GPS开关代表全部能力。
- 定位：经纬度、坐标参考系、采集时间、精度半径；地图坐标系和版本必须可比。不把不同坐标系的数据直接计算。位置陈旧、精度范围接近危险余量、疑似邻洞或跳点时降级并核实，不给固定万能精度阈值。
- 球场：球场/发球台/洞号、已核验的平面几何、目标类型与距离算法、旗位有效日期；缺失字段显式为空，附数据质量与版本。
- 球手：已授权档案、与本杆相关的历史统计及样本量/条件、当日状态、本杆对话和已经讨论的选择；不上传完整私人聊天来换取选杆。
- 输出：面向用户的话语、当前交流阶段（了解/核实/讨论/待选择/执行/静默）、事实依据、未知项、候选与最终选择的区分、待确认记录或记忆更新提案。

模型输出的记录提案不是已落库事实。APP负责确认绑定、工具权限、幂等写入、版本冲突和成功回执；迟到回复不得覆盖已进入下一杆的状态或向正在击球者播报。定位切洞可产生候选；按 [交互约定](interaction-agreement.md) 校验可靠性、缺分和允许主动问分的偏好后，可择机询问上一洞成绩及允许的细节。不自动结算或强制启动下一杆策略对话。断网、位置不可用或接口失败时保留已有可信信息，并说明哪些实时判断做不了。

## 使用越多，具体学到什么

长期了解来自授权的可检索数据，不是技能文件自行训练了模型。区分三层：原始事件（发生了什么）、统计/假设（可能有什么规律）、已确认偏好与能力。每个推断可回溯证据、样本、条件与版本；不把球童之前的建议或未执行候选当用户事实再训练回自己。

| 积累方向 | 何时有证据 | 如何改善下一次交流 |
|---|---|---|
| 真实球杆表现 | 击球与杆号、终点、球位已确认，落地/总距类型明确 | 用本人常态与失误范围讨论，而非记住最远一球 |
| 不同球位的可靠打法 | 可比较的球道、长草、沙坑等样本 | 优先讨论已经练熟且实际奏效的选择，不强加新技术 |
| 球洞经验 | 同球场、同发球台、可比较地图/旗位与条件 | 提醒上次的选择与结果，先问这次想法，不自动照抄 |
| 决策习惯 | 有本杆意图、讨论、选择与结果，跨场重复且用户认同 | 识别急于追回、临场犹豫等候选模式，用用户接受的方式沟通；不诊断人格 |
| 支持方式 | 用户明确反馈或授权偏好 | 知道何时听、何时讲方案、哪些话让他更紧张 |
| 体能与时段变化 | 多场可比记录与疲劳自报，不只看后九总杆 | 提出待验证的节奏或难度调整，不把距离变化直接归为体能问题 |
| 生活与关系延续 | 自愿分享且授权的喜好和经历 | 在相关时自然接续话题，不在击球前突然提私人往事 |

没有确认挥杆/球杆，只能有位置记录，不能更新球杆距离；没有落地观测，起终点距离不能更新落地画像。若起点与终点误差已足以左右比较，标低置信或不纳入统计；没有可辩护模型，不把误差当作可消掉的小数。

## 每场闭环与授权

1. 赛前：载入当前用户已授权且与本场有关的历史，确认本场目的与有无变化；不重新采访全部资料。
2. 场中：按约定主动关照并随时响应，不要求每杆交谈。事件记录获授权时，可按既有范围记录决定与结果，无需每杆反复索取同一授权；这不替代本杆方案共识，也不替代成绩确认。低打扰优先，不为补全样本要求用户每杆报数。
3. 赛后：先核对成绩与关键事件，少量展示“这场观察到”“可能的规律”“建议更新”的区别。用户可跳过复盘，不影响正常陪伴。
4. 更新：如已明确允许自动更新球技统计，可在授权范围内从有效事件重算；新增长期偏好/敏感心理叙述遵循伙伴记忆授权，不因经常使用而默认全量保存。只有一次表现的变化保留为本轮观察，不永久改能力。
5. 下次：用相关记忆减少问题，维持主动/被动交互约定；用户纠正优先。换球杆、球型、训练阶段后分开观察，新旧样本不盲目合并；历史的时效和条件比简单平均更重要。

可以提供：个人球场备忘、熟悉球洞的主/备用方案讨论、针对一个瓶颈的训练计划与复查、可比场次的进步记录、用户认可的沟通习惯。不能承诺持续使用必然降杆；选择性记录、漏杆、只咨询难球会产生样本偏差，不能把咨询样本当整场全部击球。

## 数据控制与未来升级

用户可查看“你记得我什么”和推断依据，纠正事件后应使依赖它的统计失效并重算；删除已授权记忆时同步处理可管理的检索摘要与衍生结论，保留必要删除标记防止旧设备恢复。APP实现用户隔离、必要数据最小化及离线同步；本技能不声称已经完成这些后端能力。

以后加入海拔时先核验数据类型、垂直基准、精度、地图版本与起终点高差，不能把手机偶发高度读数视作球场测绘。加入果岭坡面时还要核验覆盖范围、分辨率、当前旗位、速度与表面条件；有坡度不等于能可靠精确读线。新增数据通过验证后才开启相应能力，并继续遵守正式比赛功能边界。旧数据不能倒填为过去当时已知信息，也不能用新图事后否定当时合理决策。


## 可扩展服务与证据要求

- 球包与距离空档：相似条件下比较不同球杆的距离分布、可用球位和失误成本。记录场次数不是自动换杆阈值；少用某杆不等于该杆无用。可建议做对照练习或专业试杆，不由GPS落点诊断杆身、倾角或挥杆生物力学问题，不直接推动购买。
- 新球场准备：只有真实球场资料与个人样本足够时才做能力匹配与主/备用计划；讨论可实现的目标范围，不保证破80/保85。正式差点计算与单场成绩预测分开，缺少相应数据和有效模型时不输出伪精确概率。
- 节奏与状态关心：可在用户授权、宿主支持且非击球准备时提醒休息或询问状态；定位停留、打得更远、心率升高都不能独立证明焦虑、斗气或体能不足。若以后接入可穿戴，需明确授权、测量质量与上下文，先核实本人感受，不自动触发选杆或心理结论。
- 高光回顾与分享：按用户请求生成球童口吻的文字/语音稿，只用确认的事实；导出录音、合成音频与发布是不同能力。默认先给用户预览，不自动发社交平台，不顺带暴露坐标、同组人身份或私人对话。
- 知识库：规则优先当前官方原文和适用当地规则；技术与心理内容保留可靠来源及适用条件，不把名教练姓名当论据，不虚构其原话。授权资料才可入库。结构化事实和事件适合数据库，叙事检索可按需要增加向量索引，向量库不是长期记忆的必要前提，也不是事实真伪或权限的裁判。

能力升级的重点是建议质量、可信度和用户自主，而非制造依赖。支持用户查看、导出和删除可管理的个人资料；导出不包含他人无关信息或应用秘密，不以“换APP就失去伙伴”作为限制数据迁移的设计理由。


## 教练计划上下文

赛前与赛后首先传入服务偏好及其适用范围（陪伴、按需策略、是否接受练习建议，与相处风格分开）、当前教练偏好（未选择/开启/关闭）、本场暂停范围与设置版本，关闭/暂停时禁止触发教练计划、达标评估或提醒；定位更新不能覆盖此偏好。仅在持续跟进开启时，上下文包含当前唯一的主要教练计划、版本、基线、指标口径、前几场反馈与上次继续/巩固/换重点的理由；计划输出属于待用户接受的更新提案。数据结构与判断流程见 [跨场教练](coaching-cycle.md)。没有这部分跨场状态，不能声称已经核验前几场建议的改善效果。


## 主动交互上下文

APP还应传入首次形成的交互约定、静默与临时暂停范围、缺分事件与去重/取消状态、定位换洞证据、当前是否可播报及版本。按 [主动关照与响应](interaction-agreement.md) 校验后才发声；球员不主动说话不等于授权全部提醒，也不能由没有对话推断漏杆。


## 问距与上一杆事件

“还剩多少”按 [交互约定中的问距流程](interaction-agreement.md) 产生终点候选与实际杆号补问，不等同于无条件挥杆检测。APP需传入上一有效击球起点、当前球旁位置证据、杆号是否实际确认、同位置重复问距/是否漏杆或救济、起终点候选状态、事件去重与记录授权；问距请求不能自动增加挥杆数。当前球位仅开启下一起点候选，不自动生成新击球。默认仅写入可靠水平起终点距离，不自动播报，也不当成落地距离；“刚才打了多远”的查询读取同一记录，不新建事件。


## 稀疏交流与洞后核对

上下文需区分已确认击球、候选位置、漏记未知段与用户自报习惯。洞后核对推杆数；+2及以上且过程不清再核实罚杆事实，参见 [记分流程](player-and-round.md)。总杆、推杆、罚杆均明确时可求未知击球数量，不能恢复其具体球位、杆号或结果；GPS未观察空中轨迹不作挥杆检测。OB/遗失/罚杆区事件和罚杆数分别存储，含罚杆总杆不重复累加。


## 反馈与版本边界

个人服务反馈、物理校准与全局学习遵循 [持续改进规范](service-improvement.md)。APP应提供个人反馈事件、偏好版本、估计/确认分层与改进提案的读写能力；默认估计不进入未标注的真实能力统计。整体聚合、训练、地图核验与版本发布是不同基础设施，SKILL本身不能自动实现，也不能把个体使用授权扩大为跨用户训练许可。


## 实打距离引擎契约

模型启用、输入质量、候选球杆/弹道、基准环境、联合归因账本、缺失标记与可复算输出，按 [透明实打距离](playing-distance.md) 提供。原始水平距离与等效需求分开存储，后者不能回写成测量值；高差当前不可用而不是0。APP与技能分别校验规则、模型可用性和最终一致性，不能让生成话术代替数值引擎。


旧的简化弹道反求原型保留为显式research模式，仍需弹道参数；当前carry混合入口见下文v0.1.1与 [算法说明](weather-algorithm.md)，API只提供输入，不自动完成模型校准。


### v0.1.1混合模型接入更新

原始天气适配后可调用mode=hybrid，不要求外部先算调整码数，也不要求球速/旋转。profile需carry、同杆/球/弹道分组与明确baseline_id；缺方向/carry/有效天气拒绝补偿。混合模型缺当地压力时标记标准气压假设并降级，旧弹道research模式仍严格要求压力。阵风单独传入；温湿度只联合建模，再做Shapley归因，不能再叠加旧的温度/湿度调整值。详情与校准提案见 [v0.1.1算法](weather-algorithm.md)。


## 首次说明与缺失球位

按 [渐进了解与缺失处理](onboarding-and-missing-data.md) 一轮一个问题，记录首次说明/未答问题的进度，避免重复欢迎采访；“五场或更多”是相处预期，不是精度阈值。APP位置与球位分开标记，漏杆/救济间断不跨段连成一杆。[shot_evidence.py](../scripts/shot_evidence.py) 是可调用的结构化证据门控，不是已接通的GPS检测。
