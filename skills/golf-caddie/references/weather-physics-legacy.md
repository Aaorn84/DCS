代码：[scripts/weather_engine.py](../scripts/weather_engine.py)。纯Python标准库，无需网络、API密钥或第三方包。可直接导入函数或命令行输入JSON。当前是已实现的研发计算原型，测试验证数值与约束，不代表已通过真实球场精度验证；程序不会授权正式选杆。

## 一、空气密度与风：不需要球员弹道也能计算

温度T用摄氏度，Tk=T+273.15；相对湿度RH用0—100%，当地绝对气压p用Pa。使用NWS液态水近似求饱和水汽压，再按干空气与水蒸气理想气体混合计算：

```
es = 611 * 10 ** (7.5*T / (237.3+T))       # Pa
 e = (RH / 100) * es
rho = (p-e)/(287.05*Tk) + e/(461.5*Tk)    # kg/m³
```

实现支持-10至45°C、70至108kPa；低于0°C仍为相对液态水的研发近似，不做冰面公式/冻结条件外推。同温同压下，增加水汽使该模型空气密度降低；不能因此推出雨天一定飞更远，湿球、杆面接触与滚动不在本模型内。温度这里只改变大气状态，不模拟球体温度导致的初速变化。气压是计算密度所需变量，不是从未知海拔猜出来的“额外修正”。

风向按气象“从哪里来”，目标方位与风向均为真北顺时针度数。delta=风来向-目标方位：

```
wind_forward = -speed * cos(delta)       # 正值顺风，负值逆风
wind_left = speed * sin(delta)           # 正值吹向目标线左侧
```

静风允许方向为空，有风方向不可缺失。不接受无标注风级、“两格风”或未经转换的km/h。站点气压不能使用sea-level pressure代替；风的观测高度、取样与当地代表性由API适配/APP保留并核验，程序不虚构高度修正。

来源：公式取自 [NWS水汽压计算](https://www.weather.gov/media/epz/wxcalc/vaporPressure.pdf)，密度为两种理想气体分压公式之和；风来向约定参见 [NWS风向说明](https://www.weather.gov/hfo/windbarbinfo)。这些资料支持基础物理，不构成高尔夫补偿精度认证。

## 二、弹道与实打距离：已实现，需提供有效球杆参数

模型以球的相对空气速度 u = 球速 - 风速计算阻力和升力，重力向下：

```
D = 0.5 * rho * A * Cd * |u|²
L = 0.5 * rho * A * Cl * |u|²
A = pi * (diameter/2)²
```

使用四阶Runge–Kutta积分，第一次穿越水平落地平面时插值计算carry与侧向漂移；正侧偏为左。升力方向取固定后旋轴与u的叉积，Cd/Cl为调用者提供的有效常数。基本受力形式参见 [NASA阻力方程](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/drag-equation/) 与 [NASA升力方程](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/lift-equation/)。NASA方程不提供个人球杆系数。

**简化条件**：沿全程均匀水平风、固定后旋轴、有效常Cd/Cl；不模拟转速衰减、侧旋曲球、随高度风变化、阵风时序、降水、地面反弹/滚动或起终点高差。因此不能把它称为完整商业弹道引擎。

实打距离通过反求而非固定加码得到：

1. 对指定球杆/弹道和允许的初速区间，在当前环境中求刚好达到目标纵向carry所需的初速。
2. 用相同初速与弹道参数，在明确的基准环境中再飞一次。
3. 第二次的基准carry即该模型的等效需求。侧风漂移另列，不直接变成瞄准偏移；转动目标线会改变风分量，真要补瞄点需另行联立求解与风险判断。

程序先检查初速区间内距离采样是否单调，超出范围或不单调就拒绝外推。未知高差始终标明“采用水平落地平面假设，高差未计入”；传入非空高差时直接拒绝，不能无声忽略。数值反求不等于球员可以随意控制初速，该值只用于模型映射，不当作场上发力指令。

### 个人参数如何取得

profile必须提供profile_id、实际参数来源、carry类型、发射角、有效Cd/Cl、球质量/直径及适用初速范围。没有经验证的通用默认参数。本模块尚不实现自动拟合；可以接入获得授权的发射监测/球型模型，或后续用已知发射条件、carry、飞行时间/顶点等多种观察标定，再用独立样本验证。仅凭GPS总距、杆号和三场球无法唯一识别这些参数，不能伪称已完成个性化。

“常系数模型”仅在经验证的小范围近似有效；风温变化使轨迹超出标定条件时需模型评估/拒绝输出，不可只相信数字输入通过检查。当前程序状态始终research_only_not_field_validated、recommendation_allowed=false，调用者不得删除标记给用户冒充验证结果。

## 三、范围、归因与来源

weather_scenarios可提供最多24套完整天气情境；分别反求，加上名义情境取有限情境的最小/最大值。这是输入敏感性范围，**不是80%置信区间，也不包住所有可能结果**；未输入的环境误差、参数误差、个人散布与未知高差均不在范围内。没有情境时只给模型点估计，范围为null，不能人工加“±3码”。

分项账本固定采用“气压→温度→湿度→风”的顺序，每步对全模型重新反求，与上一步求差。非线性交互归到后加入的项，顺序改变归因会改变；不是各因素独立因果效应。另列数值反求残差，程序检查：原始距离+所有条件修正=最终模型结果。原始浮点数用于核对，UI四舍五入须另处理，不能口播微小残差。

weather每组必须含source、observed_at（含时区）、wind_sampling_note、pressure_kind=station。实时调用按当前UTC与显式max_weather_age_seconds检查未来/过期数据；允许阈值是APP按场景设定的配置，不是天气必然有效的保证。baseline是历史基准，单独保留来源；不拿其历史时间当当前天气。API适配仍需保证各字段单位、站点、观测时刻与来源真实，不能把同一时间戳伪装成各字段实际观测时间。

## 四、直接使用

在技能目录运行测试：

```sh
python3 -m unittest discover -s tests -p 'test_weather_engine.py' -v
```

合成参数与天气样例：[assets/weather-example.json](../assets/weather-example.json)。仅用于研发演示，不是任何真实球手或现场天气。历史回放：

```sh
python3 scripts/weather_engine.py assets/weather-example.json --as-of 2026-11-06T07:00:00Z
```

样例水平目标160码，名义环境计算得到基准等效约167码，提供的三种情境覆盖约164—172码；这是合成参数演示，不能转成用户当前的选杆建议。输出保留完整分项与metadata。

正式接入代码时可直接导入：

```python
from scripts.weather_engine import calculate
result = calculate(request)  # 当前UTC；不使用演示--as-of伪装实时
```

request.mode='atmosphere' 时不需要profile/baseline，仅计算密度与风分量，不输出补偿距离；仍需目标距离、方位、天气与时效参数。request.mode='research' 才进入弹道反求。mode='competition'/'recommendation'均拒绝；未来实战版本须独立经过规则和精度发布流程，不能仅改开关。

## 五、已验证与未验证

测试覆盖：干空气参考值、温湿压密度方向、无风/逆顺横风与方位旋转、真空解析解极限、步长收敛、侧风镜像、反求还原、米码一致、分项守恒、情境范围、缺数据/过期/未来时间/海平面气压/超域输入拒绝。它们证明这套实现按所定义模型工作，不证明真实球场误差已可接受。

API接入前可继续离线验证；上线前还需真实天气质量校验、个人参数标定、独立carry测试、目标环境覆盖与APP事件/语音接线。当前无需也不会调用付费天气服务。
